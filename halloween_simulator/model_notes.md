# Halloween Price Lab v3.3：用利润与活动完成率作决定

本课堂模型让学生只决定 **$1–$100 的整美元票价**。每次输入票价后，页面自动选择一个利润最接近该价格平均利润的真实模拟夜晚，播放游客移动、排队和聚集。学生结合**平均利润**和**活动完成率**比较试过的价格。票价是模拟器唯一经营变量；小组另外制定自己的最低完成率，作为评价方案的标准。课堂问题是：**哪个已试票价满足我们的标准，而且利润更高？我们有什么证据支持这个建议？**

地图、客流、消费意愿、活动时长和成本都是虚构教学假设，不是对实际公园的预测。学生页面显示用于比较价格的两个汇总指标：平均利润，以及完成两个活动的游客比例。用学生能理解的话解释第二项：**每 100 位入场游客中，平均有多少位完整玩完 Costume House 和南瓜屋。**普通页面与全屏视图使用同一组汇总结果。代表夜晚的实际利润和完成率仅作为后台单晚数据，不冒充页面的汇总指标。课堂不安排随机性或概率教学，也不要求学生切换夜晚、计算平均数或证明全局最优。每个圆点代表一位游客，颜色表示行走、排队、参与活动或野餐休息。

## 1. 学生改变什么，什么保持固定

- 学生只改变经营方案的票价。员工、时间、活动容量、材料与路线不变。小组的最低完成率是判断方案是否可以接受的标准，不改变模拟过程。
- 固定 8 位员工：入口 2 人、Costume House 2 人、Pumpkin House 3 人、Picnic Area 1 人。
- 一晚累计最多接待 **400 位付费游客**，按入口抵达顺序接待。这是整晚售票上限，不是同时在园人数上限。
- Costume House 同时最多 20 人；Pumpkin House 同时最多 24 人；两处满员后按先到先服务排队。
- 每人随机选择先去哪个房屋，完成后前往另一个。完成两项活动后到不限人数的 Picnic Area 社交休息，再步行离场。
- 6:00 PM 开始，7:30 PM 停止新抵达，8:00 PM 两项活动关闭。野餐最迟在 8:30 PM 结束，随后步行离场。员工班次固定为 5:45–8:45 PM。
- 入口登记时间简化为零。房屋容量表示可同时参与活动的人数，员工并非一对一服务台。

## 2. 利润怎样计算

| 固定成本 | 每晚金额 |
|---|---:|
| 人工 | $600 |
| 南瓜屋全部材料 | $800 |
| 布置与清理 | $400 |
| **总计** | **$1,800** |

`ticket income = price × admitted guests`

`profit = ticket income − 1800`

材料已经包含在固定预算中，不再单独决定供应包数量。票款只来自获准入场的人；未完成活动不退款。没有额外的逐客材料费、加班费或野餐收费。即使无人入场，利润仍为 −$1,800。

低价通常吸引更多人，但每张票收入较低；高价每张票收入较高，但可能少卖很多票。因此，“人最多”和“票价最高”都不必然带来最高利润。排队及活动轨迹帮助学生理解场内发生什么；它们不会额外改变这里的售票收入与固定成本。

## 3. 第二个指标：多少游客完成了两个活动

每位获准入场的游客都在分母内。只有在 8:00 PM 关门前或恰好关门时，**完整结束 Costume House 和 Pumpkin House 两个活动**，才计为完成。只完成一个、在排队、仍在前往下一个活动的路上，都不算完成两个。Picnic Area 的停留不是第三项必须完成的活动，被售票上限拒绝的人不在分母内。

单晚数据：

`completedBoth = number of admitted visitors with completed === true`

`completionRate = completedBoth / admitted`

页面的汇总完成率合并同一组 1,000 晚的所有入场游客：

`totalCompletedBoth = sum of nightly completedBoth`

`avgCompletionRate = totalCompletedBoth / totalAdmitted`

比例以 0–1 储存，显示百分比时乘 100。每位入场游客权重相同，**不是把 1,000 个单晚百分比直接求平均**。利润则仍按夜晚等权求平均。这两个指标分别回答“每晚平均赚多少钱”和“每 100 位入场游客中，平均有多少位完成 Costume House 和南瓜屋”。

“每 100 位”是解释比例的统一尺度，后台并非只取 100 人，也不保证任意一组 100 人或每个夜晚恰好有这么多人完成。例如 77.0% 表示每 100 位入场游客中平均约 77.0 位完成两项活动。小数表示汇总比例，不表示实际存在一部分游客；讨论是否达到小组标准时，应保留页面显示的小数，不再约成整数人数。

若一晚无人入场，`completedBoth=0`、`completionRate=null`。若全部夜晚均无人入场，`totalCompletedBoth=0`、`avgCompletionRate=null`，显示 N/A 或破折号，不能解释为 0% 或 100%，也不能据此声称满足最低完成率。有人入场但无人完成时，完成率才是 0。

| 演示票价 | 平均利润／晚 | 所有入场游客中的两项活动完成率 |
|---|---:|---:|
| $20 | $3,041.46 | 77.0% |
| $10 | $1,606.65 | 51.7% |
| $30 | $3,004.44 | 94.6% |
| $50 | $1,680.85 | 97.6% |

这些百分比来自每晚真实路线中既有的完成记录，没有新增扣分、表情或满意度评分。完成率增加不等于每位游客都能完成；它也不会改变票款或成本。

小组应先说明自己的最低完成率，再用 CER 作推荐：

- **Claim（主张）：**推荐一个票价，说明它满足小组怎样的最低完成率。
- **Evidence（证据）：**引用两个汇总指标，并比较至少一个其他已试票价。
- **Reasoning（推理）：**说明小组的最低完成比例为什么合理，所选票价如何达到它，以及为什么接受对应的利润与完成比例取舍。人数或队列观察可以辅助解释，不要求学生讲出完整因果链。

“最低”采用**大于或等于**。技术判断使用未舍入的 `avgCompletionRate >= minimumPercent / 100`；不能先舍入再比较，也没有统一预设为某一个百分比。标准过高时可能没有满足条件的价格；这时应说明当前证据不支持原要求，而不是把未达标的价格叫作合格。

仅供教师核验：在当前全部 $1–$100 整美元中，若标准为至少 70%，最高平均利润的合格价为 $24（$3,129.05、86.498975%）；若为至少 90%，则为 $26（$3,117.82、90.004600%）；若为至少 95%，则为 $31（$2,964.92、95.430917%）。这些是假设标准下的核验结果，不是学生的统一门槛或预先给定答案。最高可实现汇总完成率约为 98.412162%（$99），所以至少 99% 或 100% 在当前范围内无解。

学生材料的完成率百分比统一**向下保留一位小数**：`Math.floor(rate * 1000) / 10`，不采用四舍五入。例如 $10 的原始完成率约 51.774030%，显示 51.7%；$32 的原始值约 95.974042%，显示 95.9%。推荐小组选择**整数百分比**作为最低标准；这样，显示值是否大于或等于整数门槛，与原始比例是否达标一致，不会因显示进位误判。模型、JSON 与 CSV 仍保留原始比例；教师维护和自动判断继续使用未舍入值。这个显示规则不会改变完成率的计算口径或实际结果。用“每 100 人”的说法时也保留相同数字：68.9% 应读为“每 100 人平均约 68.9 人完成”，不能另行约成 69 人后再与最低 69% 比较；前者仍未达到 69%。

## 4. 后台情境保持不变（供教师与维护者参考）

页面仍使用原有 `classroom-2026` 情境库的 1,000 个夜晚，索引为 0…999。固定的生成规则预先确定天气、潜在客流，以及每位候选游客的最高愿付价格、到达时间、路线、活动时长和步速。给定票价后，愿付价格不低于票价的人会抵达入口，再受 400 人售票上限约束。

所有票价使用同一批后台情境，因此两项汇总指标的比较基础一致。**实际播放的夜晚则按每个价格分别挑选，可能来自不同的情境索引。** 不应把不同价格的两段动画说成“同一晚只改变票价”的严格对照。

提高价格时，愿意来的人是低价时愿意来的人的子集。达到售票上限后，实际入场人员不一定嵌套：过滤掉一些早到者后，较晚者可能获得名额。`turnedAway` 只指到达入口却被累计售票上限挡下的人，不包含本来不愿买票者。

这些是后台计算规则，课堂不需要介绍分布、种子、夜晚索引或概率公式。本次从原有路线记录汇总活动完成情况，没有改变引擎的客流、路线、活动时长、容量、成本或代表夜晚选择。

## 5. 代表夜晚的选择规则

对当前整美元票价 p，先计算相同 1,000 个夜晚的完整结果，再取未四舍五入的平均利润：

`average profit = sum of 1,000 nightly profits / 1,000`

从这些真实结果中，选择 `abs(nightly profit − average profit)` 最小的夜晚。若多个夜晚并列，选择**最小索引**，即按索引顺序遇到的第一个；不能用“后一个覆盖前一个”的并列处理。比较时使用精确计算值，不能先把均值四舍五入到美元或美分。

选定后，按相同票价、seed 和 index 重新取得该晚的完整游客轨迹。动画和当晚利润来自同一个真实模拟结果。没有复制、删除游客来凑平均人数，也不把平均利润冒充这晚的售票收入。

| 演示票价 | 代表夜晚实际入场人数 | 代表夜晚实际利润 | 平均利润／晚 | 实际利润与平均值之差的绝对值 |
|---|---:|---:|---:|---:|
| $20 | 242 | $3,040 | $3,041.46 | $1.46 |
| $10 | 341 | $1,610 | $1,606.65 | $3.35 |
| $50 | 70 | $1,700 | $1,680.85 | $19.15 |

上述实际入场人数都是整数，且利润严格符合 `票价 × 实际入场人数 − $1,800`。不同票价的最小收入变动单位不同，所以代表利润不必恰好等于平均利润。

**“代表”只指利润接近平均，不能推出这晚的完成率、队列、到达节奏、天气或活动时长也接近各自的平均。** 例如，这三个示例在 7:00 PM 的 Costume House／南瓜屋队列分别为 0／14、29／54、0／0。这些是选中夜晚的实际队列，可用于观察，不能称为平均队列。

课堂把两项汇总指标作为已经算好的比较数字即可，不安排逐晚切换或平均数计算演示。学生先提出标准并预测、看动画中一个变化、记录平均利润和完成率，再尝试新的价格；不应只凭队伍长短判断利润或总体完成率。为避免误读，页面只展示两项汇总结果，不另列代表夜晚的实际利润或单晚完成率。

各价格的平均入场人数仍为：$20 是 242.073、$10 是 340.665、$50 是 69.617。原有客流和利润均值、每晚固定成本及不设完成率条件时的最高利润价格均未改变。加入小组自定标准后，合适的推荐价格可能不同。学生应报告“已测试且满足我们标准的价格中，利润最高的一个”，而不是凭少量试验声称证明了全局最优。

## 6. 地图与队列如何工作

地图是 1000×600 的示意坐标：入口 (170,430)、Costume House (285,180)、Pumpkin House (755,180)、Picnic Area (750,440)、出口 (935,530)。固定路径连接入口与房屋、两座房屋彼此、房屋与野餐区，以及房屋／野餐区与出口。

步行时间为节点间欧氏距离除以个人步速；步速服从 Uniform(64,96) 示意单位／分钟。路径距离和时间会改变到队顺序、活动完成机会与离场时间。动画直接读取相同的逐人事件轨迹。坐标不是米，模型不模拟道路拥堵、碰撞或绕行。

房屋严格先到先服务。同一时刻先处理活动结束，再处理关门与抵达。只有某人的活动能在 8:00 PM 前或恰好结束时，才允许开始。临近关门的队首若已来不及完成，会等到关门，后面的人不能越过；因此最后几分钟可以同时出现空位和队列。关门后未开始者离场，不再继续剩余活动。已完成两项的人才能去野餐区。

`completed` 和 `completedActivities` 保留路线状态，并用于汇总完成率；`waitMinutes` 用于验证队列，不额外新增学生指标。默认地图下所有游客都会在固定员工班次结束前离场。

## 7. 代码与维护

`engine.js` 不依赖第三方库，版本为 `3.3.0`。浏览器导出 `window.HalloweenSim`，Node.js 导出 CommonJS。

```javascript
const H = require('./engine.js');
const price = 20, seed = 'classroom-2026';
const results = Array.from({ length: 1000 }, (_, index) =>
  H.simulateNight(price, { seed, index, trace: false }));
const summary = H.summarize(results);
const selected = results.reduce((best, result) =>
  Math.abs(result.profit - summary.avgProfit) <
  Math.abs(best.profit - summary.avgProfit) ? result : best);
const night = H.simulateNight(price, {
  seed, index: selected.index, trace: true
});
const state = H.stateAt(night, 60);
```

`simulateNight` 返回价格、情境、需求、入场／被拒人数、收入、固定成本、利润、`completedBoth`、`completionRate`、最后离场时间及离场人数。`trace:true` 额外含游客与 `walk/queue/activity/picnic` 轨迹；`trace:false` 的收入、客流结果相同。

`stateAt(night,t)` 返回 `guests, counts, arrived, exited`。每个动画圆点使用 `id, kind, location, from, to, progress, slot`。时间段采用 `[start,end)`；活动结束立即释放位置，游客离场立即移除。队列的 `slot` 是当前队列顺序。`arrived` 是已获准入场且已经到达的人数，不包含被拒者。

`summarize` 返回每晚等权的 `avgProfit, avgRevenue, avgFixedCost, avgDemand, avgAdmitted, avgTurnedAway`，以及 `runs, totalAdmitted, lossProbability, noAdmissionProbability`。新增 `totalCompletedBoth` 和 `avgCompletionRate`，后者按总完成数除以总入场数计算。学生只需读取平均利润与百分比，不需要阅读全部教师诊断字段。

`validatePrice` 接受 $1–$100 的有限数字；课堂页面限制为整美元。`generateScenario` 与 `simulateScenario` 供教师和测试构造情境，`resolveConfig` 按固定成本分项求总成本。修改模型后应检查：同种子复现、需求嵌套、容量与 FIFO、路线连续、关门规则、人员与现金流守恒、空场仍付固定成本。展示层还应核对所有整美元价格的最小利润差、并列首个索引，以及所选轨迹与无轨迹计算的实际人数和利润一致。还应测试无入场、有人但零完成、部分完成、全部完成、恰好关门完成，以及人数不同的夜晚合并时的分母。各价格原有的 1,000 晚利润均值不应改变。

命令行示例（教师用）：

```text
node cli.cjs --plans plans.json --runs 1000 --seed classroom-2026 --out results.json --csv results.csv
node tests.cjs
node build.cjs
```

引擎版本为 3.3.0；代表夜晚挑选仍属于展示层。当前维护核验数据保存于 `work/completion-return/verified-results.json`，包含全部 100 个票价的平均利润、平均入场人数、汇总完成率、分子分母与代表夜晚索引，以及不同假设标准下的教师核验结果。新版课堂以自定标准、两项证据和 CER 解释为主线；旧逐晚差异演示、单一利润目标与游客 rating 评分材料不作为本课依据；当前引擎不再计算或输出 rating。
